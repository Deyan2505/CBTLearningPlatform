# 06 — QA Strategy

**Актуализация Phase 0E (2026-07-29):** пълните 13 потребителски потока с acceptance criteria (включително accessibility и mobile) вече са документирани в `22_USER_FLOWS.md` — заменят по-раншния кратък списък по-долу като детайлен източник на истина за E2E покритие.

## Нива на тестване

- **Unit тестове:** бизнес логика без UI/инфраструктура — напр. изчисляване на прогрес, валидация на упражнение, парсване на съдържание от файлове. xUnit проект, добавен във Фаза 1.
- **Integration тестове:** зареждане на реално съдържание от файлове, рендиране на Blazor компонент с реални данни, работа с бъдеща база данни (когато се въведе).
- **End-to-end тестове:** критични потребителски потоци (виж по-долу) през реален браузър (напр. Playwright), добавени, когато има поне един завършен модул за тестване (Фаза 4+).

## Критични потребителски потоци (задължителни за E2E покритие)

1. Нов посетител достига начална страница → разбира какво е платформата и какво НЕ е.
2. Посетител отваря модулния каталог → влиза в флагманския модул → чете урок.
3. Потребител попълва интерактивно упражнение (thought record) → вижда резултат → може да редактира/изтрие.
4. Прогресът на завършените уроци се пази при презареждане на страницата (local storage).
5. Disclaimer/безопасностни съобщения се виждат на всяка страница с психологическо съдържание.

## Accessibility проверки

- WCAG 2.1 AA като целево ниво.
- Клавиатурна навигация за всички интерактивни елементи.
- Видим focus state.
- Семантичен HTML и landmarks (`main`, `nav`, `header`, `footer`).
- Контраст на текста, проверен инструментално (напр. axe DevTools) при всяка нова страница/компонент.
- `prefers-reduced-motion` се уважава за анимации.

## Responsive проверки

- Минимум три чупки: мобилен (~375px), таблет (~768px), десктоп (~1280px+).
- Проверка на четимост на текстовите блокове (ограничена ширина на ред).

## Security проверки

- Server-side валидация на всички входни данни (никога само client-side).
- Без тайни/API ключове в repository (проверка чрез `.gitignore` + secret scanning в CI).
- HTTPS/SSL задължителен в production (Фаза 8).
- Преглед на зависимости за известни уязвимости преди всеки launch.

## Content QA

- Всеки урок минава през процеса в `07_CONTENT_GOVERNANCE.md` преди публикуване.
- Проверка за коректна терминология и липса на диагностични формулировки.

## Визуален QA

- Ръчен преглед на нови страници/компоненти спрямо дизайн системата (Фаза 2) преди merge.

## Regression проверки

- CI изпълнява целия тестов пакет (unit + integration) при всеки push/PR.
- E2E пакетът се изпълнява поне преди всеки deployment към production.

## Критерии за приемане (шаблон)

За всяка задача/user story:
- Функционалността работи според описанието в `09_BACKLOG.md`.
- Няма нови build/lint грешки.
- Съответните тестове са добавени и минават.
- Достъпност и responsive поведение проверени за засегнатите екрани.
- Документацията (`00_PROJECT_OS/`) е актуализирана, ако решението засяга архитектура, статус или backlog.

## Definition of Done

Задача се счита за завършена само когато:
1. Кодът съществува и е merge-нат в основния branch.
2. Проектът се компилира без грешки.
3. Необходимите тестове са написани и минават.
4. Няма очевидна регресия в засегнатите потоци.
5. Документацията е актуализирана (`02_CURRENT_STATUS.md`, при нужда `03_DECISION_LOG.md`, `04_CHANGELOG.md`, `09_BACKLOG.md`).
6. Резултатът е проверен спрямо acceptance criteria на съответната user story.
7. Промените са описани в handoff доклад и в `10_SESSION_LOG.md`.
8. Няма съзнателно скрит недовършен проблем.

## Deep Learning Week — Definition of Done v3 (Сесия 42, 2026-08-22)

Заменя v2's точка 8 ("минимум 3 истински графични учебни визуализации") с две gates, одобрени в
`00_PROJECT_OS/_blueprints/COGNITIVE_LEARNING_ARCHITECTURE_v1.md` v1.1 §16/§17/§18. Точки 1–7 и
9–22 от v2 остават непроменени (виж следващия раздел). Точка 8 вече е:

**8а. Cognitive Representation Coverage** — заменя механичното броене с преценка:
1. Всеки major knowledge cluster е изрично оценен за най-подходящата представяне — документирано
   решение, не подразбирано.
2. Ключовите отношения (не йерархия) имат Concept Map поддръжка.
3. Ключовата йерархия има Mind Map поддръжка — Preview + Review състояние на една и съща структура.
4. Последователните процеси са Process Diagrams.
5. Условната логика е Decision Tree.
6. Major разграничения имат Comparison Matrix.
7. Memory Anchor се използва само когато има ясна mnemonic function — без задължителен минимум
   или максимум (0, 1 или 2 могат да бъдат напълно правилни).
8. Визуалите остават source-grounded.
9. Нула декоративен визуален шум — всеки визуал проследим до конкретна учебна функция.
10. Accessibility fallback присъства за всеки graph/tree/network визуал, генериран от **същите**
    данни като визуала (не втора, ръчно поддържана версия).

**8б. Retrieval Practice Coverage** — нов gate: всеки major knowledge cluster е оценен за подходящ
retrieval method (attempt-before-reveal / reconstruct / label-blank-map / ordering /
explain-before-reveal). Не е нужно всеки cluster да има собствено упражнение, но решението трябва
да е съзнателно, документирано (одитна таблица Cluster×Recognition/Retrieval/Application/Reasoning).
Retrieval не трябва системно да е нула през целия модул. `<details>`/`<summary>` сам по себе си
**не** се брои за retrieval, освен ако не предхожда изрична recall/reconstruct/predict/explain
подкана — само reveal на готово обяснение е recognition/explanation, не retrieval.

## Deep Learning Week — Definition of Done v2 (Сесия 39, 2026-08-14, ИСТОРИЧЕСКИ — заменена от v3 по-горе)

Собственически одобрен нов стандарт (`WEEK6_v2_DEEP_LEARNING_BLUEPRINT.md` v1.1 §13/§20/§23),
допълва — не заменя — общия Definition of Done по-горе, специфично за седмиците от
Systematic Curriculum Expansion, преработени в "дълбочинен модул" формат (пилотирано на
Седмица 6 v2). Задача от този тип се счита за завършена само когато:

1. Пълен прочит на релевантната глава от реалния текст (не резюме от паметта на проекта).
2. Идентифицирани knowledge units (Chapter Coverage Matrix).
3. **100% units accounted for** — всеки unit има статус Included/Deferred (с explicit destination)/Excluded (с explicit причина); `≥90%` е официално отхвърлено правило, никога не се използва.
4. Terminology Map, реално преброена — нито един ключов термин без обяснение.
5. Основна теория, задълбочен нюанс (deep dive), множество конкретни примери.
6. Case-based приложение с нови, самостоятелно измислени фиктивни персонажи.
7. Поне едно смислено практическо взаимодействие, където темата позволява — не token quiz.
8. Реално визуално обучение — минимум 3 истински графични учебни визуализации (не само styled text cards), с explicit класификация (graphic diagram / SVG illustration / source artifact / styled card).
9. Section checks след всеки основен блок.
10. Сериозен финален тест, покриващ Recall/Understand/Distinguish/Apply/Analyze.
11. Обяснителна, source-grounded обратна връзка навсякъде — никога голо "Верен/Грешен".
12. First-session/scope precision (или еквивалентна source-scope точност за темата) — изрично проверена с grep одит, не приета по подразбиране.
13. Source traceability — всяко твърдение проследимо до конкретен knowledge unit.
14. Safety QA — explicit third-person/observational framing документирана за всеки чувствителен елемент.
15. Accessibility QA, Visual QA (структурна, с прозрачен метод), функционални тестове — зелени, отразяващи реалния нов обем.
16. **Собственически learning review** — последната gate. Дори при зелени тестове/build/coverage, задачата остава `AWAITING OWNER LEARNING REVIEW`, не `COMPLETE`, докато собственикът не потвърди, че модулът реално учи.
